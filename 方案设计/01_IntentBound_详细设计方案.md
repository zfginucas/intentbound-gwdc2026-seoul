# IntentBound - Personal AI 外卖消费授权与审计

> 状态：开发设计稿，不代表下述功能已经实现。餐厅、菜单、报价和配送状态可使用明确标注的演示数据；Kiln 调用、模型用量、合约状态和交易哈希必须来自真实运行。
>
> 当前决定：以供应方通知的 Kiln qwen3-32b 作为实际演示模型，保留型号变更通知。挑战原文仍写 gpt-oss-120b，README 和答辩应如实说明替换。

## 1. 核心定位

**产品名：** IntentBound

**副标题：** Your agent can choose dinner. It cannot choose your limits.

**README 一句话功能声明：**

> IntentBound is a policy-enforced wallet for a personal food-ordering agent that lets users approve, monitor, stop, and independently audit delegated testnet spending.

**面向用户：** 忙于工作、愿意让 Personal AI Agent 代为选餐和下单，但不愿把无限额钱包交给模型的人。

**只解决一个问题：** 用户委托 Agent 花钱后，如何保证它没有越过用户批准的金额、商家和时间边界，并在事后让陌生人仅凭记录复核。

**产品原则：**

1. AI 理解偏好并提出候选；金额和权限不能由 AI 自行决定。
2. 模糊授权必须被澄清为用户可编辑、可确认的结构化条款。
3. 支出边界由确定性代码和受限资金出口执行，不能只靠提示词。
4. 成功付款与拒绝付款都要有可检查的理由和时间线。
5. 区块链证明授权状态、收款地址、金额和交易，不证明外卖真实送达。

这不是“会推荐外卖的聊天机器人”。它是以外卖为第一个容易理解的场景，展示 Personal Agent 的可执行消费委托与证据层。AP2 等行业协议是趋势背景，不宣称本作品实现或发明这些协议。

## 3. 单一主故事

主角 Mina 正在 GWDC 会场调试作品，不能反复看手机。她希望 Personal Agent 帮忙挑一份温热、不含香菜、能送到会场的晚餐。她愿意委托“选择”，却只批准一次有限的“消费权”。

**用户输入：**

> 帮我在会场附近点一份温热的晚餐，不要香菜。今晚 20:00 前下单，含配送费、服务费和税最多 18 测试 TRX，只能从我批准的 Seoul Bowl 或 Han Table 购买。

Agent 可以使用 Mina 明确保存的口味偏好与配送位置挑选菜品。如果用户只说“别太贵”，模型不得暗中把它解释为 18；界面必须要求用户填写并确认明确上限。配送地址与个人口味不写到公链。

**戏剧冲突：** 菜价看似合规但加费超支；更便宜的商家其实不在白名单；真正合规的商家完成付款；用户随时撤销授权。

**一句话开场：**

> A payment receipt tells us who got paid. It does not tell us whether my agent was allowed to pay.

**一句话结尾：**

> The breakthrough is not an AI that can order dinner. It is an AI that can prove why it was allowed to pay.

## 4. 演示数据剧本

所有餐厅名称、菜品照片、报价、ETA、订单号和配送状态均为明确标注的模拟商户数据。真实测试网收款地址在部署后注入，不在设计文档中编造地址或交易哈希。

**授权草案：**

| 字段 | 演示值 | 执行者 |
| --- | --- | --- |
| 本次会话总额 | 18 测试 TRX | 合约 |
| 单笔上限 | 18 测试 TRX | 合约 |
| 允许商户 | Seoul Bowl、Han Table 对应的收款地址 | 合约按地址，不按名称 |
| 失效时间 | 用户确认后 10 分钟，界面显示精确 KST 时间 | 合约 |
| 用户偏好 | 温热、无香菜 | Agent 用于推荐，非链上财务约束 |
| 支付资产 | TRON Shasta 测试 TRX | 链上以 SUN 为整数单位，界面显示测试 TRX |
| 网络手续费 | 由演示 relayer 账户承担 | 不计入用户外卖预算，并在收据中说明 |

全价计算定义为：

~~~text
orderTotal = items + deliveryFee + serviceFee + tax - discount
~~~

对用户的“18 all-in”承诺针对该订单付款总额。若将来由用户承担链上 gas，必须重新定义和展示总成本，不能沿用此口径。

| 尝试 | 模拟报价 | 结果 | 必须可见的证据 |
| --- | --- | --- | --- |
| A：隐藏的费用 | Seoul Bowl，菜价 15 + 配送 2 + 服务 2 = 19 | 拒绝：19 > 18 | 完整算式、OVER_LIMIT、决策 ID、无付款 |
| B：相似名称商家 | Han Table Express，合计 14，收款地址不在白名单 | 拒绝：商户地址不匹配 | 地址对比、MERCHANT_NOT_ALLOWED、无付款 |
| C：合规商家 | Han Table，菜价 13 + 配送 2 + 服务 1 = 16 | 允许并付款 | 真实测试网交易哈希、合约事件、订单收据 |
| D：撤销后重试 | 同一批准商家的 1 测试 TRX 饮料追加项，原本在剩余 2 额度内 | 拒绝：用户已停止 | 撤销交易状态、REVOKED、无追加付款 |

A 和 B 是满足赛题的两次不同越界尝试；D 展示人类停止权。每次尝试都拥有独立决策 ID、策略版本、报价快照和时间。若 D 的模拟追加项没有真实订单意义，现场应称它为“撤销回归测试”，不要说用户真的又买了一份外卖。

## 5. 用户工作流

### 5.1 授权前

用户打开的第一屏就是 Dinner Run 工作台，不是营销首页。左侧是 Personal Agent 对话与偏好，中央是餐厅与候选餐品，右侧是预算与授权状态。

Agent 根据 Kiln 返回的候选餐品 ID 进行推荐。模型不能自己创建不存在的商家或价格；服务器只接受模拟目录里实际存在的 ID。任何缺失预算、商家地址或时限的授权草案都不能进入付款流程。

### 5.2 授权确认

用户在结构化确认页逐项查看：总预算、单笔上限、含费口径、允许商户地址、到期时间、用途和停止方式。用户可以修改，修改后重新计算摘要。钱包确认前状态始终是“未授权”。

首版由用户测试网钱包发起创建/注资会话交易，这笔交易本身证明钱包主人批准了链上策略。后续可研究 TRON 账户权限或可验证消息签名；单有签名、但 Agent 仍握着可直接转账的主钱包私钥，不叫强制边界。

### 5.3 点餐与付款

Agent 先从商户工具取得商品和报价。报价需要包含商品金额、配送费、服务费、税、优惠、商户收款地址与有效期。规则引擎复算合计并提出付款请求。合约再次检查金额、允许商户、到期、剩余预算与撤销状态，只有通过才转出会话资金。

商户模拟器在观察到真实测试网付款后返回模拟订单号和状态。界面分别显示“测试网付款已发生”与“模拟商户已接单”，不能把二者合成一个未经证实的“真实外卖已送达”。

### 5.4 观察、停止与复核

用户可随时看到授权版本、余额、每次尝试及原因。点“停止”后，应用立即停止发起新尝试；链上撤销交易确认后，硬性授权正式失效。确认期间界面显示“正在撤销”，不提前宣称链上已停止。

收据可导出为证据包。审计者打开独立页面，不连接钱包，也能读证据包与链上事件，复算一次付款是否符合当时批准的条款。

## 6. 前端设计

### 6.1 信息架构

| 页面 | 主要内容 | 演示价值 |
| --- | --- | --- |
| Dinner Run | 对话、候选餐品、含费报价、常驻授权面板、活动时间线 | 让评委一眼看懂谁在决策、谁在限制 |
| Review Permission | 可编辑预算、允许商户、期限、完整费用口径、钱包确认 | 明确“用户批准的是结构化授权” |
| Decision Inspector | 逐项规则检查、算式、收款地址、拒绝代码、是否提交付款 | 突出两次拒绝是正确结果 |
| Receipt | 授权摘要、商品与费用、收款地址、合约事件、真实哈希 | 对应成功付款 |
| Public Audit | 输入会话或导入证据包后独立复算 | 对应第三方审计 |
| Inference Usage | 按意图解析、菜单选择列实际 token、延迟、generation ID | 对应 Kiln 与效率验收 |

桌面端建议用 3 栏不套卡片的工作台：左 28% 对话和偏好，中间弹性宽度展示带清晰食物照片的候选及状态，右 25% 常驻预算、白名单、到期时间与醒目的停止按钮。底部一条活动时间线连接授权、拒绝、付款和撤销。移动端改为对话/菜单/活动三个视图，预算与停止按钮保持可触达，收据和审计独立全屏。

界面要丰富但不拥挤：真实感食物照片、显眼的商品与配送费用拆分、订单进度、规则检查、哈希复制与区块浏览器入口、加载/失败/待确认状态。视觉底色以白和深墨色为主，青绿色表示已批准，朱红色表示拦截，金黄色用于价格提醒；不要做一屏大 Hero、单色渐变或层层嵌套的卡片。重复菜品卡片圆角不超过 8px。

顶部和视频角落始终标示当前证据模式，例如“模拟商户目录 / Kiln 实时调用 / TRON Shasta 测试网”。这些标签由实际运行状态驱动，未连通时不得写“实时”。页面应保留链确认延迟、API 错误、未授权、余额不足和证据缺失的明确状态。

### 6.2 画面中的四个记忆点

1. 用户把“别太贵”改成明确的 18 all-in，并亲手确认。
2. 大字显示“15 + 2 + 2 = 19 > 18”，付款被拦，余额不变。
3. 仿冒商家更便宜，但收款地址不在白名单，仍然被拦。
4. 合规付款出现真实交易哈希；审计页独立复算后给出通过结论。

如果时间允许，审计页可加一个“假设重放”控件：把上限从 18 调到 15，原本 16 的付款会显示“在假设授权下不通过”。必须清楚标注这是反事实分析，不是更改用户已签署的真实授权。

## 7. Agent 设计与技术取舍

### 7.1 真实要做的 Agent 能力

采用受控的工具使用工作流，而不是让模型无上限自由循环：

~~~text
理解需求 -> 请求用户补齐缺失权限 -> 读取菜单
-> 比较候选 -> 读取完整报价 -> 确定性规则检查
-> 合约尝试付款或记录拒绝 -> 收据/审计
~~~

Kiln qwen3-32b 负责理解口味、提取非财务偏好、在限定目录内比较候选、用自然语言解释推荐。代码负责校验模型输出格式和候选 ID、计算含费总额、执行时间/金额/地址边界、调用合约和生成可复核收据。对缺失、无效或矛盾的模型输出，停止并让用户确认；不能“猜一个值继续付款”。

个人化记忆只放已获用户同意的低风险偏好，如“温热”“不要香菜”“送到会场”。用户可查看和修改。地址与历史偏好不写到公链；不要以一次演示冒充复杂的长期记忆系统。

Agent 的商户接口先采用明确的工具契约，例如 searchMenu、getQuote、submitOrder、getOrderStatus。只有实际接入 MCP SDK/server 时才称“MCP 集成”；普通函数包装不能在 PPT 上冒充 MCP。商家简介或菜单说明属于不可信输入，不能改变预算和白名单；可准备一条“忽略预算”的菜单注入文本用于安全演示，但优先级低于核心闭环。

### 7.2 技术名词的正确位置

| 技术 | 本次定位 | 汇报措辞 |
| --- | --- | --- |
| Kiln qwen3-32b | 必须真实集成 | Agent 用它理解需求和选择候选，展示实际请求/用量 |
| Human-in-the-loop + 确定性策略 | 核心能力 | 用户确认，代码与合约执行；模型没有否决或放宽规则的权力 |
| 受限消费合约 | 核心能力 | 资金只能经受控出口转出，不能被 Agent 直接划走 |
| TRON 账户权限或消息签名 | 完成核心后再研究 | 只在真实钱包与验签流程跑通后才称集成 |
| MCP | 可选加分 | 真正实现工具服务器后再称集成 |
| AP2 / UCP | 行业背景 | 可说“与 Agentic Commerce 的授权方向一致”；不要说兼容或集成 |
| x402 / A2A / ERC-8004 | 扩展方向 | 不直接服务本次外卖付款闭环，最多一笔带过 |
| 跨链账户抽象 | 不列入本次交付 | 不把其他链的账户标准误称为 TRON 原生能力 |
| ZK / LTL / “节能 75%” | 不作为成果 | 未实现、未测量就从主汇报移除 |

## 8. 链上执行与证据设计

### 8.1 网络与资金

本次选择 TRON Shasta 测试网和原生测试 TRX，先实测领币、节点、区块浏览器与合约部署。合约以 SUN 整数运算，前端换算为测试 TRX；这不是法币价格，不得把测试 TRX 的数值暗示为真实外卖售价或美元。

首版由用户钱包创建会话并注入限定额度。Agent 只持有支付 gas 的 relayer 权限，不持有用户主钱包密钥，也不能绕开会话合约直接转出用户资金。合约状态至少有 owner、agent、token、总上限、单笔上限、已花费、允许商户地址、到期时间和 revoked。

**建议合约操作：**

- createSession：用户创建并资助本次限额授权；记录 policyId/policyHash。
- attemptSpend：Agent 提交收款地址、含费金额、报价哈希；合约检查金额、商户、到期和撤销，再决定转账或拒绝。
- revokeSession：用户停止授权；合约更新状态，剩余资金可按实现方案退还。

建议发出 SessionCreated、PaymentExecuted、AttemptRejected、SessionRevoked 事件。若拒绝时直接 revert，拒绝事件不会留在链上；此时必须保留可检查的应用决策日志，汇报也只能说“应用记录拒绝”。如果采用“不转账、发出 AttemptRejected、正常返回”的方式，才能展示真实链上拒绝事件。不能把前端红字当成链上证据。

首版合约至少强制收款地址、转账总额、累计额度、截止时间和撤销。它无法从链上独立证明菜品真的无香菜或商户如约送达。若要证明报价来自商户，可在下一阶段让模拟商户签署含商品、费项、金额、收款地址、订单 ID 和失效时间的报价，并由审计器验证。

### 8.2 可导出的证据包

每个会话和每次尝试使用稳定 ID。审计包至少包含：

~~~text
sessionId, policyVersion, owner, chainId, token
approvedBudget, perPaymentCap, allowedMerchantAddresses, expiresAt
approvalTxHash, revokeTxHash (if present)
quoteId, itemId, merchantAddress, items, deliveryFee
serviceFee, tax, discount, orderTotal, quoteExpiry, quoteHash
decisionId, decisionCode, decisionTimestamp, modelGenerationId (if used)
paymentTxHash, blockNumber, eventIndex (only when real)
fixtureDisclosure, schemaVersion
~~~

链上不放用户姓名、配送地址、原始聊天记录或完整偏好；只放执行所需状态和哈希。审计器要重新计算费用、查询链上策略及事件、核对报价哈希与收款地址、检查时间/累计额/撤销状态，最后给出“符合这份财务授权”或具体失败原因。审计结论不等于证明食物质量和实际配送。

建议前端使用 React/TypeScript 与成熟组件/图标库，TRON 链上调用使用 TronWeb 或同类成熟 SDK，合约使用 TRON 兼容的 Solidity。Kiln 密钥只保存在服务端环境变量，绝不送到浏览器。根目录现有 Kiln_API 是敏感文件，建仓库前先加入忽略规则并检查提交内容；如曾公开，立刻轮换密钥。

实际 Kiln 响应按“意图解析”“菜单比较”“可选解释”分别记录请求数、输入/输出 token、延迟和 generation ID。规则拒绝尽量不再调用模型，在用量页真实显示“0 additional model calls”。

能源页还需给出一张标为“情景估算，非 Kiln 实测”的表，列出假设的单请求分摊功率、推理时长代理值、计算公式及未知项。可采用 E_est(Wh) = P_alloc(W) × t(s) / 3600，明确 P_alloc 的依据；若仅有端到端延迟，说明其中混有网络与排队时间，不能称为 NPU 实际推理时长。没有同任务、同口径的 GPU 对照数据，就不计算“节能百分比”。

### 9.1 必须可重复的验证用例

| 用例 | 预期结果 |
| --- | --- |
| 用户只说“别太贵”，没有明确数值 | 进入授权补全，不产生付款权限 |
| 模型返回目录外商品或无效字段 | 客户端校验失败，不产生付款请求 |
| A 含费 19、上限 18 | OVER_LIMIT，余额与已花费不变，留下拒绝记录 |
| B 名称近似但地址不在白名单 | MERCHANT_NOT_ALLOWED，不能转出资金 |
| C 合规 16 | 链上转账或转账事件与收据金额、地址、报价哈希一致 |
| 用户已撤销后提交 D 的 1 额度追加项 | REVOKED，证明拒绝不是因为余额不足 |
| 修改导出证据包中的金额、地址或策略版本 | 独立审计失败并指出不一致字段 |
| Kiln 请求失败或链上交易待确认 | 界面明确显示失败/待确认，不伪装为已下单 |

## 12. 现场 5 分钟 Pitch Deck

| 页 | 时间 | 标题与主要画面 | 口播要点 |
| --- | --- | --- | --- |
| 1 | 0:00-0:32 | Who authorized dinner? 大幅产品画面，拒付状态清晰 | AI 能选餐，不等于可以任意付款 |
| 2 | 0:32-1:00 | Mina 的一条委托与普通支付收据的缺口 | 钱去了哪里与用户允许了什么是两种证据 |
| 3 | 1:00-1:20 | 用户确认的预算、商户、期限 | Qwen 理解，人批准，规则执行 |
| 4 | 1:20-3:20 | 全屏 Live Demo 或备份视频 | 两次拒绝、一次真实付款、一次停止 |
| 5 | 3:20-4:15 | 审计页与架构一图 | 合约控制资金，独立审计复算，真实交易哈希 |
| 6 | 4:15-5:00 | Kiln 用量 + 能力边界 + 扩展愿景 | 实际调用、模拟范围；外卖是 Personal Agent 消费基础设施的入口 |

台上别念架构图。先让评委看到鲜明的红色拒绝和绿色成功，再解释为什么可信。PPT 使用产品截图、真实费用算式、可扫描的哈希缩写和极少量文字；不要用六种技术 Logo 铺满一页。任何尚未完成的模块只放路线图角落，并标成 future work。

**建议英文开场 35 秒：**

> Mina is building at GWDC and asks her personal agent to order dinner. The agent can choose a meal, but should it be trusted with an unlimited wallet? A payment receipt shows where the money went, not what Mina allowed. IntentBound turns her request into a short-lived spending permission she approves. The agent can recommend; deterministic rules decide whether it may pay. Every refusal and every payment leaves evidence someone else can check.

**建议英文结尾 15 秒：**

> Dinner is the demo. The larger opportunity is accountable spending for every personal agent. We are not asking users to trust an AI with money. We are giving them a way to set boundaries and verify the outcome.

## 13. 评委问答预案

| 问题 | 应答重点 |
| --- | --- |
| 这不就是预算 if-else 吗？ | 创新是把模糊委托澄清为用户批准的限时授权，并把模型选餐、受限资金出口、停止与第三方证据连成实际产品闭环；算术必须是确定性的 |
| 为什么用链？ | 合约限制资金出口，链上状态与交易可独立查询；如果最终只做链上记录，不称“链上拦截” |
| Agent 能绕开吗？ | 不给它主钱包密钥；只允许经受限合约花会话资金；展示合约检查点 |
| 报价是否可信？ | 目前商家是模拟数据；首版可证明转账金额与捕获报价一致，商家签名报价是增强项；不证明真实履约 |
| 你们接入真实外卖平台了吗？ | 没有，商家目录、下单与配送是模拟；Kiln 调用、策略执行和测试网交易真实 |
| 这是 AP2/UCP/MCP 实现吗？ | 不是。本次是与该方向一致的产品原型；只有真正完成协议接口后才称集成 |
| 省了多少能源？ | 展示实际 token/请求/延迟；若无可比功耗测量，只给清楚标注假设的估计，不声称百分比 |
| 供应方为何不是 PDF 里的模型？ | 供应方已通知切换 qwen3-32b，保留通知；展示实际调用与用量，不伪称 gpt-oss-120b |

## 14. 真实性与发布检查

| 类别 | 可模拟 | 必须真实或清楚注明 |
| --- | --- | --- |
| 餐厅、菜品、照片、报价、配送 ETA、订单号 | 可以，统一标示模拟 | 不能暗示真实商家合作或真实履约 |
| 模型选择与推荐 | 不可伪造成实时调用 | 真实 Kiln qwen3-32b 请求、响应参与决策 |
| token、延迟、generation ID | 不可编造 | 使用 API 返回数据；能耗估算写公式与假设 |
| 钱包、合约、区块与交易 | 不可编造哈希或事件 | 真测试网操作；资产类型与网络名称准确 |
| 规则与拒绝 | 不可只做视觉动画 | 真实执行的策略判断与可检查日志 |
| 市场和协议叙事 | 可谈愿景 | 不把 AP2、UCP、MCP、ZK 或账户抽象画图冒充已集成 |

发布前逐项检查：README 功能声明；Kiln 模型变更说明；源码与运行方法；至少两个拒绝日志；一笔真实链上交易及匹配记录；授权/监控/停止/收据/独立审计；逐流程 token；能耗假设；不超过 3 分钟视频；Pitch Deck；密钥扫描；视频及截图中没有 Kiln_API 内容。
